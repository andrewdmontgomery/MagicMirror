# MagicMirror Configuration Reference (non-module)

Sources: [Custom Styling](https://docs.magicmirror.builders/configuration/customcss.html),
[Secrets](https://docs.magicmirror.builders/configuration/secrets.html),
[Cors Proxy](https://docs.magicmirror.builders/configuration/cors.html).

## Custom CSS

Upstream MagicMirror loads `config/custom.css` after all default stylesheets, so
anything in it overrides default styles. The base stylesheet is `css/main.css`;
each module ships its own CSS alongside it (e.g. `defaultmodules/weather/weather.css`).
Module targeting is by class matching the module name (`.clock`, `.weather`, ...).

**Check before assuming this applies as-written**: in a Docker-mounted deployment
like this one, `config/custom.css` may be generated by the container's own
entrypoint script at container start rather than being a real persisted file —
CLAUDE.md documents whether that's the case here. If so, hand edits to it are
silently lost on the next restart, and the durable equivalent is a custom
module's own `.css` file (a genuinely mounted, git-tracked file) instead, or a
new mount added to `docker-compose.yml` if the goal is styling a *built-in*
module's markup from outside.

Weather icon styling example (Erik Flowers' [weather-icons](https://erikflowers.github.io/weather-icons/)
set — find the class name for a given icon there):
```css
.wi-day-sunny {
  color: #ffff00;
}
```

## Secrets

Since MagicMirror 2.35.0 (beta): protect config values — API keys, tokens in URLs,
private calendar URLs, lat/lon — from being visible in the browser (they're
otherwise exposed at the `/config` subpath) by referencing environment variables
instead of literal values.

Enable it:
```js
const config = {
  hideConfigSecrets: true,
  // ...
};
```
Reference an env var with `${VAR_NAME}`; prefix with `SECRET_` for ones that should
be masked (shown as `**SECRET_VARIABLENAME**`) wherever config is displayed:
```js
config: {
  client_id: "${STRAVA_CLIENT_ID}",           // not masked — still visible
  client_secret: "${SECRET_STRAVA_API_KEY}",  // masked
}
```
**Only works server-side.** A module whose secret-needing logic runs entirely in
the browser (no `node_helper.js` doing the actual request) can't protect it this
way — the browser-side workaround is routing the request through the CORS proxy so
substitution happens server-side before the external call is made:
```js
const config = {
  hideConfigSecrets: true,
  cors: "allowWhitelist",
  corsDomainWhitelist: ["api.mapbox.com"],
  modules: [{
    module: "MMM-Flights",
    config: {
      mapUrl: "/cors?url=https://api.mapbox.com/styles/v1/${SECRET_MAPBOX_ID}/tiles/{z}/{x}/{y}?access_token=${SECRET_MAPBOX_TOKEN}",
    },
  }],
};
```
The docs are explicit that this is beta with **no guarantee**: a malicious module
could still intercept config data, and anyone with browser access to the mirror can
see whatever isn't specifically `SECRET_`-prefixed.

## CORS Proxy

Browsers block many module fetches to third-party APIs (news feeds, some weather
providers) via CORS. MagicMirror's built-in proxy routes the request through the
server instead: a module URL like `https://example.com` becomes
`/cors?url=https://example.com`, and the MagicMirror server makes the actual call.

**Disabled by default since 2.35.0** for security reasons — must be turned on
explicitly:
```js
cors: "allowAll",       // any URL — only safe if the mirror isn't reachable from outside your LAN
```
or, the safer option:
```js
cors: "allowWhitelist",
corsDomainWhitelist: ["example.com", "api.mapbox.com"],
```
Only relevant to modules that fetch an external API directly from front-end JS —
a module whose data comes through its own `node_helper.js` (server-side) never
hits CORS in the first place, since the browser never makes that request itself.
